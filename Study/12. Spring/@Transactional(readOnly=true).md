## @Transactional(readOnly=true) 사용 이유

`@Transactional(readOnly=true)`를 사용하는 이유는 무엇일까? 사용하지 않는 것과 무슨 차이가 있는가?

### Hibernate의 성능 최적화(dirty checking 건너뛰기)
JPA(Hibernate)는 영속성 컨텍스트를 통해 엔티티의 변경 사항을 감지하는 더티 체킹(Dirty Checking) 기능을 제공한다.

- 일반 트랜잭션: 변경 감지를 위해 엔티티의 "스냅샷"을 유지해야 하므로 메모리를 더 사용하고, 트랜잭션이 끝날 때 변경된 게 있는지 확인하는 CPU 연산이 필요하다.
- `readOnly=true`: Hibernate는 해당 트랜잭션 내의 엔티티들이 수정되지 않을 것임을 알고 스냅샷을 유지하지 않는다.
	- 덕분에 메모리 사용량이 줄어들고, 변경 감지 프로세스를 생략하여 성능이 향상된다.

### DB 레벨의 최적화
사용 중인 DB에 따라 읽기 전용 트랜잭션에 최적화 된 처리를 수행한다.

- MySQL: `readOnly=true` 설정 시, InnoDB 스토리지 엔진은 읽기 전용 트랜잭션에 대해 Transaction ID를 할당하지 않아 오버헤드를 줄인다.
- Replication 구조: DB가 Master(쓰기/읽기)와 Slave(읽기 전용)로 나뉘어 있을 경우, 이 옵션을 보고 자동으로 Slave DB를 바라보게 설정할 수 있어 부하 분산이 쉬워진다.

### 코드의 의도와 안전성 확보
- 가독성: 이 메서드가 "데이터를 변경하지 않는 단순 조회용" 이라는 것을 동료 개발자에게 명시적으로 알려준다.
- 실수 방지: 실수로 엔티티를 수정하는 코드를 작성하더라도, `readOnly=true`가 걸려 있으면 실제 DB에 반영(flush)되지 않으므로 의도치 않은 데이터 변경을 막을 수 있다.

## @Transactional을 붙이지 않을 때와 차이

### 지연 로딩(Lazy Loading) 동작 여부
- `@Transactional`이 없을 때: DB 조회가 끝나는 순간 영속성 컨택스트가 닫힌다. 만약 가져온 엔티티에 연관된 다른 데이터를 나중에 조회(Lazy Loading)하려고 하면, `LazyInitializationException`이 발생하며 프로그램이 뻗어버린다.
- `readOnly=true`일 때: 메서드가 끝날 때까지 트랜잭션과 영속성 컨텍스트가 유지된다. 따라서 필요한 시점에 연관 데이터를 가져올 수 있다.
### 영속성 컨텍스트와 '변경 감지'
- `@Transactional`이 없을 때: 조회된 엔티티는 '준영속 상태'가 된다. 데이터를 수정해도 DB에 반영되지 않는다. 하지만 매번 조회할 때마다 영속성 컨택스트를 새로 만들고 버리는 비용이 발생한다.
- `readOnly=true`일 때: 영속성 컨택스트는 유지하되, "이 데이터는 안 변할거야"라고 선언한 상태이다. 하이버네이트는 변경 감지를 위한 스냅샷 저장을 생략한다.

### 결론적으로 왜 써야 하는가
1. 데이터 일관성: 한 메서드 안에서 A 테이블과 B 테이블을 조회하는데, 그 사이에 다른 사용자가 데이터를 수정해버리면 결과가 꼬일 수 이싿. `readOnly=true`는 해당 메서드 동안 동일한 스냅샷을 보게 하여 일관성을 유지해준다.
2. 안정 장치: "이 서비스는 오직 읽기 전용이다"라는 것을 시스템적으로 보장한다.
3. 단순한 `findById` 하나만 호출하고 끝나는 로직이라면 안 붙여도 무방하다. 하지만 연관 객체 그래프를 탐색(Lazy Loading)하거나, 여러 번의 조회를 하나의 비즈니스 로직으로 묶어야 한다면 `readOnly=true`를 붙이는 것이 성능과 안정성 면에서 훨씬 유리하다.
